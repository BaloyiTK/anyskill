# AnySkill Data Model

**Target:** PostgreSQL 10.23  
**Milestone:** Marketplace Engine v0

## Design rules

- UUID primary keys generated by the application for PostgreSQL 10 portability.
- Monetary values are integer minor units (cents), never floating point.
- Timestamps use `timestamptz`.
- Latitude/longitude are stored explicitly in v0 so the schema works without PostGIS. A later PostGIS migration can add geography indexes without changing domain IDs.
- Authentication credentials/password hashes do not belong in profile tables. Authentication will be handled by the API/auth layer.
- Exact professional coordinates and customer job addresses are private API data.

## Relationships

```text
users
 ├── professional_profiles
 │    ├── professional_skills ── skills ── skill_categories
 │    └── professional_locations
 ├── job_requests (customer)
 │    └── quotes (professional)
 │         └── bookings
 │              └── booking_status_history
 └── reviews
```

## Core tables

### users
Application identity shared by customer and professional modes.

Important fields: email, phone, display name, avatar, account status and timestamps.

### professional_profiles
One-to-one extension of users. Stores professional bio, experience, verification status, online/accepting-jobs state, service radius and aggregate marketplace metrics.

### skill_categories / skills
Normalized skill taxonomy. A professional can offer multiple skills.

### professional_skills
Connects a professional to a skill and stores provider-specific service title, description and base price.

### professional_locations
Stores the professional's latest private latitude/longitude. Public discovery must return distance/area, not raw coordinates.

### job_requests
A customer's request to a specific professional for a skill. Stores description, budget range, requested schedule, private job coordinates and lifecycle status.

### quotes
Commercial offers against a request. Multiple quotes/counteroffers may exist; only one may ultimately be accepted.

### bookings
Created when both sides agree. Stores the agreed price and operational lifecycle state.

### booking_status_history
Append-only audit trail for booking transitions.

### reviews
Booking-bound rating from one party to the other. Unique per reviewer per booking.

## State values

Job request:
`REQUESTED | QUOTED | ACCEPTED | DECLINED | EXPIRED | CANCELLED`

Quote:
`PENDING | ACCEPTED | DECLINED | SUPERSEDED | EXPIRED`

Booking:
`CONFIRMED | ON_THE_WAY | ARRIVED | IN_PROGRESS | COMPLETION_SUBMITTED | CUSTOMER_CONFIRMED | PAYMENT_PROCESSING | PAID | REVIEWED | CANCELLED | DISPUTED`

Verification:
`UNVERIFIED | PENDING | VERIFIED | REJECTED`

## Location search v0

Until PostGIS availability is confirmed, the API can pre-filter by a latitude/longitude bounding box and calculate great-circle distance. The authoritative distance check must run server-side.

When PostGIS is available, add a `geography(Point,4326)` column and GiST index and replace distance filtering with `ST_DWithin`.

## Key integrity constraints

- email is unique case-insensitively via a unique index on `lower(email)`.
- phone is unique when present.
- professional profile is one-to-one with user.
- one active professional-skill record per professional/skill.
- service radius must be positive and bounded.
- latitude is -90..90; longitude is -180..180.
- money values cannot be negative.
- quote professional must be enforced by API to match the request recipient.
- booking customer/professional/request consistency is enforced by transaction/service logic.
- rating is 1..5.
- reviewer can review a booking once.

## Privacy boundary

Public professional search may expose:
- professional ID
- display name/avatar
- skills/services
- rating/completed jobs
- verification status
- approximate distance
- online/availability state
- base price

It must not expose:
- raw latitude/longitude
- phone/email before policy permits
- verification documents
- private job addresses
- payment identifiers
